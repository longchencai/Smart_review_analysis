## 1. 第一优先：保住「能跑」——这是唯一的真风险

### 风险是什么

项目依赖一个 **392 MB 的基座权重文件**，它不在 git 仓库里（设计如此）。
**如果下午换一台电脑演示，这台新电脑上没有这个文件，程序会直接崩在启动阶段**，
报一个很难看懂的错（`OSError: no file named model.safetensors`），现场很难快速救回来。

### 两个预案，选一个

**方案 A（强烈推荐）：U 盘整包拷贝，演示机直接跑，不依赖网络**

需要拷贝的目录（合计约 470 MB）：

```
models/bert_distillation_quantization/            ← 整个目录都拷
  ├── bert-base-chinese/model.safetensors   (392 MB) ← 最关键，必须带上
  ├── model/student_bert_4l384.pt            (59 MB)
  ├── model/student_bert_4l384_int8.pt       (15 MB)
  └── 其余 .py / .txt / .md 文件

data/processed/final_data/                 ← 如果现场要跑评估/测试，也要带上
```

演示机上还需要 **Python 环境**。如果演示机没有
`D:\conda_envs\PYTHON_ML`，最省事的做法是：**把整个 `D:\conda_envs\PYTHON_ML` 目录也拷过去**
（conda 环境是自包含的，拷过去改一下路径就能用），比新装 torch 快得多。

**方案 B：演示机现场下载（约 14 分钟，需要网络）**

```python
import os
os.environ["HF_ENDPOINT"] = "https://hf-mirror.com"
from huggingface_hub import hf_hub_download
hf_hub_download(repo_id="bert-base-chinese", filename="model.safetensors",
                local_dir=r"<项目路径>\models\bert_distillation_quantization\bert-base-chinese")
```

脚本已备好：`docs/model_audit/fetch_base.py`（改一下路径即可）。
**注意**：这条命令走镜像站，实测耗时 14 分钟，不要等到演示前 10 分钟才做。

### 到场后第一件事：验证能跑

```powershell
D:\conda_envs\PYTHON_ML\python.exe -u "D:\...\models\bert_distillation_quantization\predict.py"
```

看到 6 条样例各自输出「商品大类 + 情感 + 置信度」就说明一切正常。
**这一条命令要第一个跑，跑不通立刻换电脑或改用截图。**

## 2. 第二优先：把演示流程固定下来，不要现场自由发挥

### 主秀：`predict.py`

秒级出结果，本身就是最好的演示。建议就用它内置的 6 条样例（实测全部正确）：

| 输入 | 期望输出 |
|---|---|
| 这个键盘手感很好，打字很舒服，就是价格有点贵，整体还算满意 | 数码电子 / 正面 |
| 酒店位置偏僻，房间隔音差，前台态度也不好，不会再来了 | 本地生活 / 负面 |
| 手机屏幕显示效果不错，但是电池续航太短了，充一次用不了半天 | 数码电子 / 负面 |
| 书的内容很精彩，排版也舒服，物流很快，第二天就到了 | 图书文娱 / 正面 |
| 洗发水味道刺鼻，用完头皮发痒，果断退货 | 个护美妆 / 负面 |
| 热水器安装师傅很专业，出水温度稳定，洗澡很舒服 | **家用电器** / 正面 ← 最有说服力的一条 |

> 第 6 条留到最后讲：家用电器是全项目最难的类（训练样本仅 381 条），学生能判对，
> 是个很好的收尾点。

**另有两条可在讲「量化无损」时现场对比：**

```powershell
python predict.py            # int8，15.12 MB，0.53 秒加载
python predict.py --fp32     # fp32，59.39 MB，0.20 秒加载 → 结论应该完全一致
```

### ⚠️ 不要现场自由输入

我实测过一个反例：输入 **「书的内容很精彩，物流也很快」**（明显是好评），
模型判成 **负面评价**，置信度 0.88。情感任务整体 F1 是 0.92，本来就有约 8% 的错判，
现场随机输入很容易踩到，一旦翻车很难圆回来。

**做法**：只演示排练过的样例。如果老师/同学要求现场输入，可以接，但提前打个招呼：
「这类模型在短句上会有波动，我们看整体指标」。

### `test_predict.py` 不要现场跑

它要跑完整验证集，**实测耗时 5 分 22 秒**，现场等不起。
建议**提前跑一次并截图**，把「31 项通过 / 0 失败」那一屏作为证据展示。
截图已归档：`docs/model_audit/test_predict_result_31pass.txt`。

## 3. 该讲哪套数字 —— 三套口径不要混

| 指标 | 数值 | 出处 |
|---|---|---|
| 参数量 | 学生 **15,560,457** vs 教师 102,274,569 → **1/6.57** | 实测 |
| 体积 | fp32 **59.39 MB** → int8 **15.12 MB**（**3.93x**） | 实测 |
| 教师 390.22 MB → 学生 int8 15.12 MB | **1/25.8** | 实测 |
| **验证集** 综合 F1 | fp32 **0.9072** / int8 **0.9074** | `eval_result.txt`（仓库已有记录）|
| **测试集** 综合 F1 | fp32 **0.9082** / int8 **0.9086** | 本次补测，见审查报告 |
| **对教师保留率（测试集）** | **98.92%（fp32）/ 98.96%（int8）** | 本次补测 |
| 大类 F1（测试集） | 学生 int8 **0.8941** vs 教师 **0.8949** → 几乎持平 | 本次补测 |
| 推理速度（CPU） | int8 **11.2 ~ 19.9 ms/条** | 实测 |
| 量化耗时 | **0.47 秒** | `eval_result.txt` |

### 推荐的讲法

> 「学生在**独立测试集**上综合 F1 **0.9082**，教师是 0.9181，
> 也就是说用 **1/6.6 的参数**、**1/26 的体积**，保留了教师 **98.9%** 的性能。
> 大类识别这一项几乎追平教师（0.8941 vs 0.8949）。」

**这个说法比只报一个 0.9072 更有力**，而且完全站得住 —— 我实测过。

### ⚠️ 三个不要说的说法

| 不要说 | 原因 |
|---|---|
| 「蒸馏全流程可复现」 | 教师权重（390 MB）和蒸馏缓存都不在仓库里，现场跑不了训练 |
| 「量化后 CPU 加速 1.4 倍」当作强结论 | 这个数字随机器变化很大，实测区间 1.4x ~ 2.1x；如需说，补一句「在 XX 环境实测」 |
| 「0.9072 是最终成绩」 | 那是验证集成绩。说「验证集 0.9072，独立测试集 0.9082」更可信也更诚实 |

## 4. 明确放弃清单（今天不要碰）

| 放弃事项 | 潜在收益 | 为什么不现在做 |
|---|---|---|
| **词表裁剪** | int8 体积再降 35.5%（15.12 → 9.75 MB） | 要重新映射 id + **重训 27 分钟** + 重测，风险高、时间不够 |
| **输入长度优化（动态 padding + 分桶）** | 推理快 4~9 倍 | 改动推理路径，必须重测一致性；而且演示是交互式的，25ms 和 2ms 肉眼无差别 |
| 蒸馏重训（epochs 提到 12~16） | 预计 +0.5~1.5 点 | 需要 15 分钟以上训练 + 重测，且教师缓存缺失 |
| 换 6L/512 结构 | 预计 +1~3 点 | 等于重做整个蒸馏 |
| `torchao` / int4 量化 | 可能再压一半体积 | 环境里没装依赖，探索性工作 |
| Git LFS 整理 / 仓库瘦身 | clone 体积从 443 MB 降下来 | 与演示无关，且会影响 git 历史 |
| 修「单例半初始化」等 P0/P3 代码问题 | 报错信息更清晰 | 要动 `bert_config.py` 这个所有模块的公共依赖，演示前动它不值得 |
| `vocab.txt` 换行符、`weights_only` 等小问题 | 代码整洁 | 纯粹是整洁度，零功能影响 |

**一句话原则：从现在到上台，只做「验证」，不做「修改」。**

## 6. 可能被问到的问题（附建议答案）

| 可能的提问 | 建议回答 |
|---|---|
| 为什么学生只有 4 层 / 384 维？ | 目标是**无 GPU 部署**。层数减到教师的 1/3、宽度减半，注意力头维度与教师保持一致（都是 64），参数量降到 1/6.57。 |
| 量化掉了多少精度？ | **几乎没掉**。验证集 0.9072 → 0.9074，测试集 0.9082 → 0.9086。权重层面的相对误差只有 0.5%~1.5%，余弦相似度 >0.9998。 |
| 为什么不做量化感知训练（QAT）或静态量化？ | 试过，**在 HuggingFace BERT 上跑不通** —— FX 符号化追踪遇到 BERT 里依赖运行时数值的切片操作会直接报 `TypeError`。这是 tracing 机制与 transformers 实现的根本冲突，动态量化是当前可行路径。 |
| 家用电器这类为什么明显差？ | 训练样本只有 **381 条**，而教师自己在这一类也只有 F1 0.7867。我们也试过类别加权，反而掉了 1 个点 —— 因为加权只改决策边界，补不上信息量。**唯一的解法是补数据。** |
| 怎么保证没有数据泄漏？ | 教师软标签只缓存在训练集上；模型选择只用验证集；**测试集在整个训练过程中一次都没碰过**，最后才用。 |
| 为什么量化后指标反而略高一点？ | 差异在 ±0.0002 量级，属于随机波动。动态量化会在每次前向时按当前批次现算激活的量化范围，本身带有微小随机性。 |
| 部署需要什么环境？ | **CPU 即可，不需要显卡**。注意 int8 量化模型只能跑 CPU —— PyTorch 的 int8 算子没有 CUDA 实现（这一点我们踩过坑：对量化模型调 `.to('cuda')` 不报错，但前向时才失败）。 |
| 温度 2.0、权重 0.7 是怎么定的？ | 这是常用起点（软标签为主、真实标签为辅）。**坦白说我们还没做消融实验**（α=0 纯硬标签 vs α=1 纯软标签），这是后续要补的。 |
| 和教师比到底差多少？ | 独立测试集上，学生 0.9082 vs 教师 0.9181，**保留率 98.9%**；大类识别几乎持平（0.8941 vs 0.8949）。 |
| 这个模块的下一步是什么？ | 按性价比：① 词表裁剪（可再省 35% 体积，且不用重跑教师缓存）；② 训练轮数提到 12~16；③ 学生换成 6L/512 结构。 |
