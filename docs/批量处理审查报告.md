**`src/data_processed/`（数据管道）写得很好，基本全是向量化写法；
问题集中在 `models/`（模型模块），是"逐行循环"风格。**

## 二、逐项说明

### 2.1 🔴 训练时每 100 批评估一次完整验证集

**位置**：`models/bert/bert_train.py:92`

```python
if index % 100 == 0 or index == len(train_dataloader):
    (cat_acc, ...) = model_eval(val_dataloader, my_bert_model)   # ← 全量 9,390 条
```

**实测推算**（参数取自 `models/bert/bert_config.py:73-74`，`epochs=5`、`batch_size=16`）：

```
训练集 43,820 行 / batch=16 = 2,739 批/轮
% 100 每轮触发 27 次，加末尾 1 次 = 28 次
× 5 轮 = 完整验证集评估 140 次
验证集 9,390 行 = 587 批/次
```

**影响**：每次评估要把 587 个 batch 全跑一遍。按单次 15 秒保守估计，**仅这一项就吃掉约 35 分钟**；
若 GPU 较慢或验证集更慢，可达 1 小时以上。而 `model_eval` 用的是默认 `verbose=True`，
还会往控制台刷 140 次 tqdm 进度条，日志几乎不可读。

**另外**：`model_eval` 内部有 `tqdm`，在训练循环里被调用 140 次，I/O 开销也不小。

**建议**：改为**每轮结束评估一次**（`if index == len(train_dataloader)`），
或每 N 轮评估一次。预计训练总时长可缩短 **30~50%**，且完全不损失模型质量
（最优模型选择仍然每轮都有依据）。

### 2.2 🔴 RF 模块：重复向量化 + 数据泄漏

**位置**：`models/rf/rf_model_train.py:28-37`

```python
def train_model(label_col, tfidf_save_path, rf_save_model_path):
    y_labels = df_data[label_col]
    tfidf = sklearn.feature_extraction.text.TfidfVectorizer(stop_words=stop_words)
    words_feature = tfidf.fit_transform(x_words)          # ← 每次都重新 fit
    X_train, X_test, y_train, y_test = train_test_split(
        words_feature, y_labels, test_size=0.2, random_state=666)   # ← 切分在向量化之后
```

**问题一：重复计算。** `train_model()` 被调用两次（7 分类 + 情感），
两次都用**同一份 `x_words`**，但各 `fit_transform` 一次。
TfidfVectorizer 在 43,820 篇文档上建词表 + 算 IDF + 生成稀疏矩阵是重活，
做两遍纯属浪费。→ 应把 `words_feature` 算一次后复用。

**问题二：数据泄漏（更严重，是正确性问题）。**
先 `fit_transform(全量)` 再 `train_test_split`，意味着
**TF-IDF 的词表和 IDF 权重已经把 20% 的"测试集"看了进去**。
因此 `rf_model_predict` 报出来的那个指标是**乐观偏高的**，不能当作泛化能力。

**正确顺序**：
```python
X_tr, X_te, y_tr, y_te = train_test_split(x_words, y_labels, ...)   # 先切
tfidf = TfidfVectorizer(stop_words=stop_words).fit(X_tr)            # 只在训练集上 fit
X_tr_vec, X_te_vec = tfidf.transform(X_tr), tfidf.transform(X_te)   # 再各自 transform
```

**顺带**：`models/rf/rf_model_pinggu.py` 用的是 `config.process_test_path` 且
`tfidf.transform()`（没有 fit），这一侧是对的。

### 2.3 🟠 模块导入即加载 421 MB

**位置**：`models/rf/rf_predict_fun.py:9-17`

```python
with open(config.tfidf_save_path, 'rb') as f:            tfidf = pickle.load(f)
```

全部写在**模块顶层**（不是函数里），所以：

| 文件 | 体积 |

### 2.4 🟠 9 处 DataLoader 全部缺 `num_workers`

**位置**：
```
models/bert/dataloader_utils.py:74, 90, 94, 98
models/bert_distillation_quantization/dataloader_utils.py:76, 95, 99, 103
models/bert_distillation_quantization/distill_data.py:124   ← 显式 num_workers=0
```

全项目 `num_workers` / `pin_memory` 只出现 **1 次**（就是那个 `num_workers=0`）。

**影响**：`num_workers=0` 意味着分词（`collate_fn` 里调 tokenizer）
**在训练主进程里串行执行**。每个 batch 都是：主进程分词 → 送 GPU → 前向 → 反向 → 再分词…
GPU 在每个 batch 之间都要等 CPU 分完词。对 `batch_size=16, max_len=256` 的
BERT-base 训练来说，这是典型的**GPU 利用率被数据管道拖住**。

**建议**：
```python
DataLoader(..., num_workers=4, pin_memory=True,
           persistent_workers=True, prefetch_factor=4)
```
> 注意：Windows 上 `num_workers>0` 需要把训练代码放在 `if __name__ == '__main__':` 里
> （`bert_train.py:112` 已经这么做了 ✓）。另外自定义 `collate_fn` 依赖 `config` 单例，
> 派生进程会各自 import 一次 `Config()`，需要确认不会重复加载 BERT 权重 —— 建议实测。

### 2.7 🟡 `df.iterrows()` —— 慢 11 倍，但绝对值不大

**位置**：
```
models/bert/dataloader_utils.py:22
models/bert_distillation_quantization/dataloader_utils.py:24
```

**实测**（真实 train.csv，43,820 行）：

| 写法 | 耗时 | 单行 |
|---|---|---|
| `df.iterrows()` + `row['review']` | **1.14 s** | 26 µs |
| `zip(df['review'], df['label'], df['cat_l1'].map(cat2id))` | **0.10 s** | 2 µs |
| 提速 | **11.0x** | |

换算到一次 `build_all_dataloader()`（train+val+test 共 62,600 行）：**1.6 s → 0.15 s**。

**诚实结论**：这是教科书级的反模式，**但实际只省 1.5 秒**，对训练总时长无感。
**优先级应该排在最后**，不要为了它单独发一次改动。
（唯一值得顺手改的理由：它同时是 `read_csv` 缺 BOM 参数的位置，见 2.12，可以一起改。）

### 2.8 🟡 每个 batch 触发 5 次 GPU→CPU 同步

**位置**：`models/bert/bert_train.py:61, 63-68`、`models/bert/bert_model_eval_utils.py:40-46`

```python
total_loss += loss.item()                        # 同步 1
all_cat_true_labels.extend(batch_cat_labels_tensor.tolist())    # 同步 2
all_sent_true_labels.extend(batch_sent_labels_tensor.tolist())  # 同步 3
all_cat_pred_labels.extend(cat_pred_labels.tolist())            # 同步 4
all_sent_pred_labels.extend(sent_pred_labels.tolist())          # 同步 5
```

**影响**：`loss.item()` 和 `.tolist()` 都会**强制 CUDA 同步**（等 GPU 把结果算完再拷回 CPU）。
每个 batch 5 次同步，等于把本可以流水线并行的 GPU 计算切成 5 段串行。
2,739 批/轮 × 5 = **每轮约 13,700 次同步**。

**建议**：累积张量、每个 batch 只做一次 `.detach().cpu()`，或干脆
在需要时用 `torch.cat` 合并后再一次性 `.numpy()`。至少把 5 次降到 1~2 次。

### 2.12 ⚪ 3 处 `pd.read_csv` 缺 `utf-8-sig`

> **勘误（2026-09-22 实施时发现）**：本节初版把
> `models/bert_distillation_quantization/dataloader_utils.py:22` 也列了进来，**这是错的** ——
> 该处写的是 `pd.read_csv(csv_path, encoding=config.csv_encoding)`，本来就是对的。
> 已从下方清单移除。

项目的数据 CSV **带 UTF-8 BOM**（`data_preprocess.py:228-230` 用 `encoding='utf-8-sig'` 写出）。
实测确认 BOM 情况：

| 文件 | BOM | 说明 |
|---|---|---|
| `data/processed/final_data/*.csv` | **有** | 读取必须显式 `utf-8-sig` |
| `data/raw/online_shopping_10_cats.csv` | 无 | 所以 `data_audit.py:97`、`data_preprocess.py:117` 不需要改 |
| `models/rf/processed_data/*.txt` | 无 | `to_csv` 写出，无 BOM |
| `models/fasttext/processed_data/*.txt` | 无 | 同上 |

**真正需要修的是这 3 处**（读的都是带 BOM 的 train/val/test.csv）：

```
models/bert/dataloader_utils.py:20                pd.read_csv(csv_path)
models/bert/eda_maxlen_analysis.py:21             pd.read_csv(DATA_PATH)
models/fasttext/_02_数据处理_词级别联合标签.py:19    pd.read_csv(base_path)
```

**影响**：部分 pandas 版本会把首列名读成 `'\ufeffreview'`，
随后 `row['review']` 抛 `KeyError: 'review'`（报错信息很难指向真正原因）。
`src/data_processed/` 下的脚本都正确写了 `utf-8-sig`，说明作者知道这个坑，
只是 `models/` 下没同步。

**建议**：统一补上 `encoding='utf-8-sig'`。
