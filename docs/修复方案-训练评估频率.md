## 一、问题确认

**位置**：`models/bert/bert_train.py:91-92`

```python
# TODO 边训练边评估  每 100 批, 评估一次, 如果当前分数高于历史最高分, 记录并保存
if index % 100 == 0 or index == len(train_dataloader):
    # 调用 model_eval() 进行评估
    (cat_acc, cat_pre, cat_rec, cat_f1), (sent_acc, sent_pre, sent_rec, sent_f1) \
        = model_eval(val_dataloader, my_bert_model)          # ← 每次都是完整 9,390 条
```

`model_eval()` 内部 `for ... in enumerate(tqdm(val_dataloader))` 会**把整个验证集跑一遍**，
所以这个 `if` 每触发一次，就付出一次全量推理的代价。

---

## 二、根因分析（三层）

### 第 1 层：频次写成了「绝对批次数」，没有和「轮的大小」挂钩

| 参数 | 值 | 出处 |
|---|---|---|
| 训练集 | 43,820 条 | `data/processed/final_data/train.csv` |
| batch_size | 16 | `models/bert/bert_config.py:74` |
| **每轮批次数** | **2,739** | 43,820 ÷ 16 向上取整 |
| 触发间隔 | 每 100 批 | `bert_train.py:92` |

```
2,739 ÷ 100 = 27.4  →  每轮触发 27 次，加末尾那次 = 28 次
```

**「每 100 批」在作者的直觉里大概是「隔一会儿看一眼」，但在这份数据上
它等于「每 3.65% 个 epoch 就看一眼」** —— 一轮里看 28 次。

关键在于：这个数字是**写死的绝对值**，和数据集规模无关。数据量翻 10 倍，
它仍然是「每 100 批」，也就是每轮评估 274 次。

### 第 2 层：代价被严重放大（用项目自带日志实测）

**证据来源**：`models/bert/eval_result.txt` 里的 tqdm 记录
（对 test 集 9,390 条做评估，588 批）：

```
100%|██████████| 588/588 [01:30<00:00,  6.50it/s]
```

**一次完整验证集推理 = 90 秒**（588 批 ÷ 6.50 批/秒）。这是项目自己的日志，
不是我估算的。

于是：

| 项目 | 计算 | 结果 |
|---|---|---|
| 每轮评估次数 | 27 + 1 | 28 次 |
| 5 轮总评估次数 | 28 × 5 | **140 次** |
| **仅评估的总耗时** | 140 × 90 s | **12,600 s ≈ 3.5 小时** |
| 每轮训练耗时（估） | 2,739 批 × ≈0.4 s | 约 18 分钟 |
| 每轮评估耗时 | 28 × 90 s | **约 42 分钟** |

**结论：评估时间约是训练本身的 2.3 倍。** 一次完整训练（5 轮）
总共约 5 小时，其中 **约 3.5 小时（67%）花在重复的验证集评估上**，
而这 140 次评估里的绝大多数（135 次）对最终结果没有任何贡献 —— 因为
真正决定保存哪个模型的是那 5 次「轮末评估」，中间的评估只是在同一轮内
反复确认「模型还在变好」。

### 第 3 层：写法来自教学示例，是固定模板

第 91 行注释 `# TODO 边训练边评估  每 100 批` 的措辞，
与该模块其它地方的注释风格一致，明显沿用了课程示例的结构。
示例代码用的数据集通常很小（几千条），「每 100 批」在那里是合理的；
搬到 43,820 条的真实数据上就失真了。

**所以这不是"写错了"，而是"模板参数没有随数据规模重新标定"。**

## 四、头脑风暴：8 种可行思路

| 方案 | 做法 | 优点 | 缺点 / 风险 | 适用场景 |
|---|---|---|---|---|
| **A. 每轮评估一次** | 条件改成 `if index == len(train_dataloader)` | 改动最小（1 行）；评估次数 140→5；语义最清晰 | 一轮内完全没有验证反馈；若某轮中途出现最优（恒定 lr 下确实可能），会漏掉那个检查点 | 轮时长很短（<20 分钟），或已加学习率调度 |
| **B. 按比例评估** ⭐ | 引入 `eval_every = max(1, len(train_dataloader)//4)`，条件改成 `index % eval_every == 0 or index == len(...)` | 修复**根因**（频率随轮大小自动伸缩）；保留作者"边训练边评估"的原意；检查点粒度仍有 4~5 次/轮，模型选择质量几乎不降 | 多引入 1 个变量；仍是 20~25 次评估（比 A 多，但比现状少 85%） | **推荐**：想保留轮内监控，又不想浪费 |
| **C. 每 N 轮评估一次** | `if epoch % 2 == 0 and index == len(...)` | 评估最少 | 最优轮次可能是奇数轮 → **直接影响模型选择质量** | 轮时长很长（>1 小时），且能接受选模型变粗 |
| **D. 轮内小样本 + 轮末全量** | 轮内用 1,000 条子集快速评估，轮末用全量 | 反馈频繁且便宜 | ① 子集 macro-F1 方差大（±1 点量级）② **子集上的 best 与全量上的 best 不可比**，极易保存到"子集上碰巧好"的模型 ③ 要额外维护一个子集 loader | 轮时长以小时计、需要频繁监控时 |
| **E. 配置化（与 A/B 组合）** | 在 `bert_config.py` 加 `self.eval_every_n_batches = 0`（0=每轮一次），或在 B 的基础上把比例提成配置 | 频率可调、可写进实验记录、便于复现 | 改动面稍大（config + train） | 会做多组对照实验时 |
| **F. 不改频率，只给评估提速** | val loader 加大 batch、关掉 tqdm | 零语义变化 | **只能缓解，140 次还是 140 次**；全量前向本身不可压缩，提速上限也就 1.3~1.6 倍 | 作为辅助手段，不建议单独用 |
| **G. 轮内只看训练集指标** | 轮内不碰验证集，轮末才验证 | 轮内零额外前向 | 训练集指标不能用于选模型（会过拟合）；收益与 A 基本相同但实现更绕 | — |
| **H. 不改** | 保持现状 | 与课程示例完全一致 | 每次训练多烧 3.5 小时 | 如果作业/评分明确要求"每 100 批评估" |

## 五、推荐方案：**B（按比例评估）+ E 的轻量版**

### 为什么推荐 B

1. **它修的是根因，不是症状。**
   A 只是把 140 压到 5，但这个 `% 100` 的失真逻辑仍然留在代码里；
   下次有人把 batch_size 从 16 改到 4（批次数变成 10,955），
   B 会自动跟着变成每 2,738 批评估一次（4 次/轮），而 A 依然是 1 次/轮 ——
   两者都不会再退化。但如果数据量缩到 5,000 条（313 批/轮），
   A 会变成「一轮评估 1 次」而 B 仍然保持 4~5 次，**B 的行为不随规模漂移**。

2. **它保留了作者明确写下的设计意图。**
   第 91 行注释写着「边训练边评估」——说明作者是**有意**想在一轮之内看到进展的。
   直接改成 A 等于把这条设计意图删掉；B 是「按原意执行，但把频率归一化」。

3. **模型选择质量几乎不受影响。**
   当前该模块用的是**恒定学习率 5e-5，没有 warmup、没有调度、没有梯度裁剪**
   （`bert_config.py:75`、`bert_train.py:31`）。在这种配置下，模型在一轮之内
   先升后降是完全可能的，最优检查点未必落在轮末。
   A 会把选择粒度从 28 次/轮砍到 1 次/轮，**有可能选到比现在更差的检查点**；
   B 保留 4~5 次/轮，风险小得多。

4. **改动仍然很小**（3 行），符合最小改动原则。

### 关于「E 轻量版」

我建议把「每轮评估几次」提成配置项，而不是硬编码 `//4`：

```python
self.eval_times_per_epoch = 4      # 每轮评估次数；设为 1 即「每轮只评估一次」
```

理由：这个数值本质上是「时间 vs 监控粒度」的权衡，属于实验超参，
应该和其它超参一起放在 `bert_config.py` 里、能写进实验记录。
同时它天然覆盖了方案 A（设成 1 就行），不需要维护两套逻辑。

> **如果你觉得连配置项都不想加**，那就退回方案 A（改 1 行）——
> 我把它列为备选，改动更小，只是丢了轮内监控。

## 六、具体修改点

### 修改 1：`models/bert/bert_config.py`（新增 1 行）

在 `self.lr = 5e-5` 附近新增：

```python
        self.lr = 5e-5
        # 每轮评估几次（在轮内按比例均匀分布）。
        # 背景：原实现写死「每 100 批评估一次」，而本数据集一轮有 2,739 批，
        # 等于每轮评估 28 次 —— 单次全量验证约 90 秒，5 轮要烧掉约 3.5 小时。
        # 这里改为「每轮评估 N 次」，频率自动随数据集规模伸缩。
        # 设为 1 表示只在每轮结束时评估一次。
        self.eval_times_per_epoch = 4
```

### 修改 2：`models/bert/bert_train.py`（改 1 行 + 加 2 行）

**第 36 行附近**（进入 epoch 循环前），新增评估间隔的计算：

```python
    # 把「每轮评估 N 次」换算成批次数；保证至少为 1，避免数据集极小时除零
    eval_every = max(1, len(train_dataloader) // config.eval_times_per_epoch)

    for epoch in range(1, config.epochs + 1):
```

**第 91-92 行**，替换条件与注释：

```python
            # 边训练边评估：每轮按比例评估 config.eval_times_per_epoch 次
            # （原实现是 index % 100，在本数据集上一轮会触发 28 次）
            if index % eval_every == 0 or index == len(train_dataloader):
```

### 修改 3（可选，独立评估）：顺手关掉轮内评估的进度条

**问题**：`model_eval()` 内部无条件 `tqdm`，现在会被调用 140 次，
控制台被刷屏、日志难以阅读。

**位置**：`models/bert/bert_model_eval_utils.py:13,31`

```python
def model_eval(val_dataloader, my_bert_model):        # ← 现状：只接受 2 个参数
    ...
    for index, (...) in enumerate(tqdm(val_dataloader), start=1):
```

**建议改成**（与蒸馏模块同款做法，把已有修复回灌过来）：

```python
def model_eval(val_dataloader, my_bert_model, verbose=True):
    ...
    iterator = enumerate(tqdm(val_dataloader), start=1) if verbose \
               else enumerate(val_dataloader, start=1)
    for index, (...) in iterator:
```

调用方：轮内评估时传 `verbose=False`，轮末评估传默认值 `True`。

> ⚠️ 这一步是**可选**的，且会动到另一个文件。如果你希望本次只改「频率」这一件事，
> 就跳过修改 3，我单独出一份方案。**我倾向于把它拆开做**，便于独立回归验证。

## 八、验证方式

分三级，从快到慢，每级都有明确的通过标准。

### 第 1 级：逻辑验证（秒级，无需 GPU、无需训练）

用一段独立脚本，直接复现新老两种条件在真实批次数下的触发次数：

```python
n_batches = 43820 // 16 + (1 if 43820 % 16 else 0)      # 2739
epochs = 5

old = sum(1 for i in range(1, n_batches + 1) if i % 100 == 0 or i == n_batches)
new = sum(1 for i in range(1, n_batches + 1)
          if i % max(1, n_batches // 4) == 0 or i == n_batches)

print(f"旧: {old} 次/轮 -> {old*epochs} 次")
print(f"新: {new} 次/轮 -> {new*epochs} 次")
```

**通过标准**：旧 = 28/轮（140 次）；新 = 4~5/轮（20~25 次）。

**已实跑，结果如下**（无需 GPU，秒级）：

```
真实参数：训练集 43,820 条 / batch=16 -> 2,739 批/轮 x 5 轮
  现状 index % 100        : 28 次/轮 -> 140 次   ≈ 3.5 小时
  方案B 每轮 4 次(//4)    :  5 次/轮 ->  25 次   ≈ 0.6 小时
  方案A 每轮 1 次         :  1 次/轮 ->   5 次   ≈ 0.1 小时

  新逻辑对数据集规模的伸缩性（设每轮 4 次）：
    训练集   4,382 条 ->    274 批/轮 -> 每     68 批评估一次 = 4 次/轮
    训练集  43,820 条 ->  2,739 批/轮 -> 每    684 批评估一次 = 4 次/轮
    训练集 438,200 条 -> 27,388 批/轮 -> 每  6,847 批评估一次 = 4 次/轮
```

注意最后一段：**新逻辑在任何数据规模下都稳定保持「4 次/轮」**，
而旧逻辑会随数据量线性恶化（数据翻 10 倍 → 每轮 274 次评估）。这是选 B 而非 A 的核心理由之一。

### 第 2 级：端到端干跑（约 5~10 分钟，CPU 可跑）

在**临时目录**造一份极小数据（train 320 条 / val 64 条），
把 `epochs` 设为 1、`batch_size` 设为 16，完整跑一次 `bert_train.py`，
然后**数日志里「评估日志: 轮次」出现了几次**。

**通过标准**：出现次数 = 预期值（`320//16 = 20` 批，`//4 = 5`，
所以应为 5 次；旧逻辑在这个规模下只会触发 1 次 —— 这正好说明新逻辑在小数据上
依然保持「4~5 次」的比例语义，不随规模漂移）。

> 实现方式：不改动项目文件，用一份临时副本 + 环境变量覆盖数据路径；
> 或者用一个 wrapper 脚本 monkeypatch `config.train_path` / `val_path` 后再 import。
> 我会在实施时选最不侵入的方式。

### 第 3 级：真实训练对比（需 GPU，可选）

如果你打算真的重训教师，记录修复前后每轮耗时：

| 记录项 | 现状 | 修复后 |

（差异应在 ±0.005 以内；若差异更大，说明检查点粒度确实影响了选择，届时回退到方案 A 或提高 `eval_times_per_epoch`）。
