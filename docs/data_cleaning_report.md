## 1. 数据源与问题诊断

**数据源**：`data/raw/online_shopping_10_cats.csv`（62,774 行，UTF-8）

### 1.1 类别分布严重不平衡

| 原始类别 | 样本数 | 占比 |
|---|---:|---:|
| 平板 / 水果 / 洗发水 / 衣服 / 酒店 | 各 10,000 | 各 15.93% |
| 计算机 | 3,992 | 6.36% |
| 书籍 | 3,851 | 6.13% |
| 手机 | 2,323 | 3.70% |
| 蒙牛 | 2,033 | 3.24% |
| 热水器 | 575 | 0.92% |
| **合计** | **62,774** | 100% |

最大/最小类比值 **17.4 : 1**。前 5 类各恰好 10,000 条，说明语料是**人工截断采样**的，并非自然分布。

### 1.2 类别命名不统一

- **品牌名混入类别名**：`蒙牛` 是品牌，而其余都是品类（水果、衣服、书籍…）
- **书面语/口语混用**：`计算机`（书面）与 `手机`、`平板`（口语简称）并存
- 类别粒度不一致：既有品类（水果），也有具体商品（洗发水），还有场所（酒店）

### 1.3 标签与文本质量问题

| 问题 | 规模 | 处理方式 |
|---|---|---|
| 完全重复行（三列全同） | 0 条 | 无需处理（原脚本的 `drop_duplicates` 实际是空操作，见 §7.3） |
| 空评论 | 1 条 | 删除 |
| 超短评论（< 5 字） | 153 条 | 删除 |
| 同一文本跨多个类别 | 27 条文本 / 58 行 | **保留**（见 §8.4） |
| HTML 实体残留（`&#183;` `&hellip;`） | 49 行 | 解码 |
| URL（含无协议头的 `www.`） | 17 行 | 删除 |
| 个人隐私信息（手机号等） | 80 行 | 遮盖为占位符（见 §4） |
| 抓取残留（乱码串、页码、`Copyright?` 等） | 少量 | 部分清除 |

### 1.4 情感标签分布

`label`：1（正面）31,728 条 / 0（负面）31,046 条，整体近似均衡。但**类别内部差异明显**：

| 类别 | 正面率 |
|---|---:|
| 热水器 | **82.6%**（474/575） |
| 书籍 | 54.5% |
| 其余 8 类 | 约 50%（几乎精确对半） |

除热水器外各类都接近 50/50，说明语料在情感维度上也是**刻意平衡采样**过的。热水器是唯一明显偏斜的类。

## 2. 类别体系设计（10 → 7）

### 2.1 设计原则

按**品类逻辑**归类，而不是为了凑数量或均衡样本：

| 一级大类 | 包含的原始类别 | 原始样本 | 清洗后 |
|---|---|---:|---:|
| 数码电子 | 手机、平板、计算机 | 16,315 | 16,241 |
| 食品饮料 | 水果、蒙牛 | 12,033 | 12,019 |
| 个护美妆 | 洗发水 | 10,000 | 9,997 |
| 服饰鞋包 | 衣服 | 10,000 | 9,994 |
| 本地生活 | 酒店 | 10,000 | 9,955 |
| 图书文娱 | 书籍 | 3,851 | 3,850 |
| 家用电器 | 热水器 | 575 | 544 |
| **合计** | **10 类** | **62,774** | **62,600** |

### 2.2 三个关键决策

**① 热水器归入「家用电器」，不删除。**
热水器只有 575 条，早期版本的做法是直接删掉它。但热水器在真实电商语境中就是家电品类，删掉会让产品体系缺失一个类目。**少样本是训练问题（类别权重 / 重采样），不是数据问题**，不应该靠删数据解决。

**② 不做「把无关类别合并以均衡样本量」的操作。**
曾考虑把「酒店 + 书籍」合并成「生活文娱」以减少小类，但那是为了指标好看而歪曲品类语义，放弃。

**③ 只保留一级大类，不再输出二级小类。**
本项目任务定义为「7 个大类分类 + 情感二分类」，因此清洗阶段只把原始类别映射到大类，不再生成小类列，避免数据 schema 与任务范围不一致。

> **答辩要点**：被问「为什么是 7 类不是原始 10 类」时，回答依据是**品类逻辑归属**（如热水器属于家电），并说明迁移表见上表；被问「为什么不保留小类」时，回答任务只定义到大类层级，且部分小类与大类一一对应（如洗发水↔个护美妆），保留小类不会带来额外信息。

## 3. 清洗流程

`src/data_preprocess.py` 按以下顺序执行，每一步都有日志输出：

| 步骤 | 操作 | 变化 | 剩余 |
|---|---|---:|---:|
| 0 | 读入原始数据 | — | 62,774 |
| 1 | 映射一级大类（10 → 7） | — | 62,774 |
| 2 | 去除空评论 | −1 | 62,773 |
| 3 | 文本清洗：HTML 实体解码 → 剥离真 HTML 标签 → 去 URL → 合并空白 → **PII 脱敏** | 遮盖 80 行 | 62,773 |
| 4 | 去除清洗后不足 5 字的评论 | −153 | 62,620 |
| 5 | 去除纯符号行 | −2 | 62,618 |
| 6 | 去重（同一大类内相同文本） | −18 | **62,600** |
| 7 | 按一级大类 + 情感分层划分 70/15/15 | — | 43,820 / 9,390 / 9,390 |

合计去除 **174 条**。

### 3.1 文本清洗的具体规则

```python
html.unescape(text)                  # 1) HTML 实体解码（&#183; &hellip; 等）
re.sub(r'</?[A-Za-z][^<>]*>|</[A-Za-z][^<>]*', '', text)   # 2) 只剥离「以字母开头的真标签」
re.sub(r'https?:\S+|www\.\S+', '', text)                    # 3) 去 URL（含无协议头）
re.sub(r'\s+', ' ', text).strip()                           # 4) 合并空白
mask_pii(text)                                              # 5) PII 遮盖
```

**为什么标签正则要写成「以字母开头」**：本数据集里尖括号内容**几乎全是中文书名**（`<阿波林小世界>`、`<<十万个为什么>>`、`<穿PRADA的恶魔>`），而不是 HTML 标签。用宽松的 `<.*?>` 会把这些书名整段吃掉 —— 实测有 40 行内容被破坏。收紧后只匹配到 1 处真正的标签（一个抓取残留的乱码串 `</Feature` 类的片段）。详见 §7.1。

### 3.2 去重规则

同一（一级大类，评论文本）只保留一条。**必须放在文本清洗之后**：清洗会把仅空白差异的重复合并成相同文本，放在清洗前就抓不到。

> 关于「label 取多数票」的说法已在代码中更正 —— 实测 18 个重复组里有 17 组恰好是两条且情感相反（1:1 平票，不存在多数票），因此明确采用「保留先出现的一条」作为平票规则。详见 §7.3。

## 4. PII 脱敏

### 4.1 遮盖规则

对 **80 行**评论中的个人信息做占位符替换（而非删除整句，保留原句结构）：

| 类型 | 触发条件 | 占位符 |
|---|---|---|
| 手机号 | 11 位、`1[3-9]` 开头，两侧无其他数字 | `[手机号]` |
| 座机 | 带连字符（`0xxx-xxxxxxx`）或不带连字符（`0` 开头 10–12 位） | `[电话]` |
| 服务热线 | `400` / `800` 号码 | `[电话]` |
| 邮箱 | ASCII 邮箱格式 | `[邮箱]` |
| 微信 / QQ | 标签后跟含数字的字母数字 ID（如 `微信lic770`） | `[已脱敏]` |
| 订单 / 发票 / 运单 / 会员号等 | 标签**之后**跟长数字；也覆盖「号码写在标签之前」的写法（如 `174208675是我的订单编号`） | `[已脱敏]` |

### 4.2 设计原则：只动「有强特征」或「带明确标签」的数字

**不做「长数字一律遮盖」**。因为数据里的长数字大部分不是隐私：

- `20200411` 是保质期日期
- `55555555555`、`6666…` 是刷屏式强调
- `10000mAh`、`vx600x` 是商品型号规格

一律遮盖会破坏正常内容。因此改为「强特征（手机号格式）+ 明确标签」两条通道。这一步通过 **10 余项误伤回归测试**验证，例如 `手机mate7`、`手机g5200`、`vx600x`、`600000是我的订单数量` 都必须**不被**遮盖。

### 4.3 残留（已知未处理）

- **个人姓名与具体地址**：约 20 行含姓名、约 4 行含地址，未自动处理。原因是自动规则误报率过高 —— 例如「X先生」模式会命中 359 行，其中绝大多数是「南怀瑾先生」这类作者/公众人物，遮盖会破坏正常内容。
- **个别订单号**：1 行中是同句内用「和」并列的第二个订单号。

> **答辩要点**：被问「数据里有隐私吗」时，回答**号码类已系统遮盖（80 行）**，姓名地址因自动识别误报率高而保留，并说明如需彻底脱敏应人工核对定向处理。主动交代残留比声称"已完全脱敏"更稳妥。

## 5. 数据集划分

### 5.1 分层键：一级大类 + 情感（14 个格子）

```
stratify = cat_l1 + '_' + label     # 7 类 × 2 情感 = 14 个格子
```

### 5.2 为什么不能只按类别分层

只按类别分层时，**情感比例会在三个集合之间漂移**，导致 val 上调出的结论无法迁移到 test：

| 类别 | train | val | test | 漂移 |
|---|---:|---:|---:|---:|
| 热水器 | 83.46% | 81.71% | **72.84%** | **10.63 pp** |
| 乳制品 | 49.40% | **42.43%** | **52.48%** | **10.04 pp** |
| 手机 | 49.47% | 48.40% | 52.91% | 4.51 pp |

加入情感后的结果：

| 类别 | train | val | test | 漂移 |
|---|---:|---:|---:|---:|
| 家用电器 | 81.63% | 81.48% | 81.71% | 0.23 pp |
| 图书文娱 | 54.51% | 54.50% | 54.59% | 0.09 pp |
| 其余 5 类 | 约 50% | 约 50% | 约 50% | ≤ 0.03 pp |
| **整体** | 50.58% | 50.58% | 50.59% | **0.01 pp** |

**最差漂移从 10.63 pp 降到 0.226 pp。**

### 5.3 划分结果

| 集合 | 样本数 | 占比 |
|---|---:|---:|
| train | 43,820 | 70.00% |
| val | 9,390 | 15.00% |
| test | 9,390 | 15.00% |

**类别分层偏差**：各类在三个集合中的占比与全局 70/15/15 的最大偏差 **0.110 pp**。
**类别覆盖**：7 个大类在三个集合中都完整出现。

> **答辩要点**：这里能体现「不只是照抄 train_test_split」—— 发现并修正了分层键的选择，并用数据证明修正效果（10.63 → 0.23 pp）。

## 7. 关键技术决策与踩过的坑

这一节是清洗工作中**排查与修正**的完整记录，也是答辩最能体现工作量与严谨性的部分。

### 7.1 HTML 标签正则正在破坏中文书名（内容破坏，40 行）

**现象**：清洗后出现 `我买过>,我发现…` 这种断句，书名不见了。

**定位**：原始数据里 40 处尖括号中，**几乎全部是中文书名**（`<阿波林小世界>`、`<<十万个为什么>>`、`<穿PRADA的恶魔>`），而不是 HTML 标签；最严重的一行因开头的 `<` 与末尾的 `>` 配对，删掉了很长一段正文。

**修正**：标签正则收紧为「以字母开头」的 `</?[A-Za-z][^<>]*>`，并只额外处理残缺的闭标签片段（`</Feature` 这类）。修正后该正则在整个数据集上只匹配 1 处（一个抓取残留的乱码串），书名全部保留。

### 7.2 邮箱正则吞掉中文，静默删除了一条真实评论（数据丢失）

**现象**：一条负面评论（`不是很好@裤腿太小.码数也不对`）从数据里消失了。

**定位**：邮箱正则用了 `\w`，而 Python 的 `\w` **匹配中文**，于是整句被识别成邮箱、替换为 `[邮箱]`（只剩 4 字符），随即被「不足 5 字」规则静默删除。

**修正**：邮箱正则收紧为 ASCII-only（`[A-Za-z0-9._%+-]+@…`）。修正后该评论回到数据中。

### 7.3 去重其实是空操作（逻辑失效）

**现象**：日志里打印「去重后剩余 62,774 行」—— 一行都没删。

**定位**：`df.drop_duplicates()` 对**全部列**去重，而原始数据里完全相同的三元组是 0 条；且它位于文本清洗**之前**，清洗后才产生的重复也抓不到。

**修正**：改为清洗后按（一级大类，文本）去重。同时发现「取多数票」的描述与事实不符（18 组里 17 组是 1:1 平票），代码注释已改为如实说明平票规则。

### 7.4 交付数据无法由脚本复现（交付链路断裂）

**现象**：别人 clone 后按 README 跑一遍，得到的目录内容与仓库里的交付数据不一致。

**定位**：脚本声明会产出 3 个元数据文件，但它们既没被提交、也没有真正生成；而下游脚本又依赖其中缺失的一个，**一跑就报 `FileNotFoundError`**。

**修正**：消除重复文件（同一份信息不再存两处），让标签定义只有单一来源（`class.txt`），下游脚本改为自给自足。修正后新增**端到端复现验证**：临时目录重跑全流程，与交付文件逐字节比对。

### 7.5 座机正则误伤日期区间

**现象**：酒店评论里的入住日期 `20080503-20080508` 被遮盖成 `[电话]`。

**修正**：所有号码类正则统一加数字边界 `(?<!\d)` / `(?!\d)`，既避免在长数字中间截断（如 18 位账号里截出假手机号），也消除了日期区间误判。

### 7.6 其他已修正项

| 问题 | 修正 |
|---|---|
| 「不含中文就删」会误删合法英文评论（如 `waste of my money...`） | 改为只删「连一个中文/字母/数字都没有」的纯符号行（仅 2 行） |
| PII 计数日志与交付数据不符（打印 64，实际 63） | 计数移到去重之后，保证与交付一致 |
| 脚本日志找不到「去除 174 条」这个总数 | 合并冗余的长度过滤步骤，日志直接输出合计 |
| EDA 图 9 在非 Windows 机器上崩溃 | 字体改为跨平台探测，找不到中文字体时**跳过该图并提示**，不再中断 |

## 8. 已知局限

> 这一节建议**主动讲**。答辩时被追问「数据有什么问题」而答不上来，比主动说明局限要被动得多。

**8.1 「乳制品」子类可被单个词识别。**
原始数据中该类的类名就是品牌名「蒙牛」，重命名后仍有 **99.8%** 的评论字面包含「蒙牛」（2,033 条，现并入食品饮料）。因此涉及该子类的样本存在捷径特征，相关指标会偏高。

**8.2 关键词基线不可忽视。**
不做任何训练，仅用各类别高频词打分的规则分类，一级大类可达 **47.8%** 准确率；情感任务用「好评/满意/垃圾/太差/失望」等词计数可达 **78.15%**。报告中应把这两个基线一并列出，否则模型效果会显得虚高。

**8.3 建议 `max_len` 取 256 而非 128。**
有 **10.2%** 的评论超过 128 字，且多为长评论（图书文娱类中位数 145 字），用 128 会整条截断；超过 510 字的仅 0.49%，512 上限不构成问题。

**8.4 存在跨类别的重复文本，并造成少量 train/test 重叠。**
有 **27 条文本、58 行**（0.09%）出现在多个大类下，多为「一般一般一般」这类不含品类信息的套话；另有 1 条文本同时带两种情感标签。由于去重只作用于同一大类内部，这些文本在划分后会落到不同集合：

| 泄漏形式 | 规模 |
|---|---|
| 归一化后完全相同的文本出现在 train 与 test | 26 种（占 test **0.28%**） |
| 近似重复（相似度 ≥ 0.90） | test 43 行（**0.46%**） |
| 近似重复（相似度 ≥ 0.85） | test 51 行（**0.54%**） |

**影响上限约 0.5 个百分点**，不足以显著抬高准确率。当前选择**保留**这些行（它们是真实存在的评论）；如需严格消除，可按文本做全局去重。报告里不宜以个别模板句作为泛化能力的证据。

**8.5 `家用电器` 类的指标统计上很脆弱。**
该类仅 544 条且 **81.6% 为正面**（全数据集唯一明显偏斜的类）。按（大类，情感）分层后，其「负面」格子只有 train 70 / **val 15 / test 15** 条，n=15 时 95% 置信区间约 ±25 个百分点，**per-cell 指标基本是噪声**；同时 macro-F1 会被这个 0.87% 的小类主导。**给出 per-class 指标时必须同时列出 support（样本数）**。

**8.6 仍残留少量未遮盖的姓名、地址与个别订单号。** 见 §4.3。

```bash
# 环境
```

**两个必须注意的读取细节**（已写进 README）：

## 10. 答辩预设问答

**Q1：为什么把 10 类合并成 7 类？依据是什么？**
按品类逻辑归属，迁移表见 §2.1。例如手机/平板/计算机同属数码电子，水果/蒙牛同属食品饮料。

**Q2：热水器只有 575 条，为什么不删掉？**
它是真实存在的家电品类，删掉会让产品体系缺一个类目。**少样本是训练问题（类别权重/重采样），不该用删数据解决**。同时我们在局限里如实说明它 81.6% 正面偏斜、per-cell 指标不可用。

**Q3：62,774 条少了 174 条，具体少在哪？**
1 条空评论 + 153 条不足 5 字 + 2 条纯符号 + 18 条重复。脚本每一步都有日志，合计 174 条可从日志逐项对上。

**Q4：怎么保证清洗没有把有用信息洗掉？**
这是我们踩过坑的地方：早期宽松的 HTML 标签正则会吃掉中文书名（40 行受影响），我们定位后收紧正则为「以字母开头的真标签」，现在交付数据里 53 处尖括号已逐条确认为书名/表情/比较符。另外清洗全程只做「去噪」不做「改写」，且每一步都可复现。

**Q5：数据里有个人隐私吗？**
号码类已系统遮盖 **80 行**（手机号、座机、热线、邮箱、QQ/微信、订单号等），采用占位符替换并保留句式。**姓名与地址未处理**，因为自动规则误报率过高（「X先生」会命中 359 行，绝大多数是作者名），如需要应人工核对后定向处理 —— 这一点我们写进了已知局限。

**Q6：数据划分是怎么做的？**
70/15/15，分层键是**一级大类 + 情感**共 14 个格子。只按类别分层会让情感比例在集合间漂移最多 10.63 pp（热水器、乳制品），导致 val 上的结论无法迁移到 test；加入情感后最差漂移降到 0.226 pp。

**Q7：你的数据可信吗？怎么验证的？**
三重验证：① 残留噪声自检全部为 0；② 重跑脚本 7 个文件 SHA256 逐字节一致；③ 提供只读审计脚本 `data_audit.py`，本报告所有数字都可用它一键复核。此外做过端到端复现：临时目录重跑全流程与交付文件逐字节比对。

**Q8：训练集和测试集有泄漏吗？**
有少量，且我们量化了：归一化后完全相同的文本出现在 train 与 test 的占 test **0.28%**；相似度 ≥0.90 的近似重复占 **0.46%**。**影响上限约 0.5 个百分点**，不足以显著抬高准确率，来源是数据集本身的模板句（如「不错不错…」）。我们选择保留这些真实存在的评论，并在报告中注明。

**Q9：数据不平衡怎么处理？**
清洗阶段不通过删数据来"平衡"，而是保留真实分布（数码电子 25.9% vs 家用电器 0.87%）。训练阶段可用类别权重或重采样，**评估时必须以 macro-F1 为主并同时给出每类 support**。

**Q10：为什么 class.txt 的顺序不能改？**
它的行序就是标签编号 0–6，同时是 `train.txt` 等文件里类别编号的定义。改动顺序会让所有已生成文件的标签含义整体错位。因此标签定义只有这一个来源，`config.py` 也是从它派生而不是另抄一份。

**Q11：别人拉下来能跑吗？**
能。原始数据与清洗结果都已入库；脚本用 `__file__` 定位路径，任何目录下都可运行；五个脚本互相独立、没有隐藏依赖。

**Q12：清洗中你觉得最有价值的一条改进是什么？**
**修正分层键**：发现情感比例在集合间漂移 10 个百分点，改为「类别 + 情感」分层后降到 0.23 个百分点 —— 这直接决定了后续所有实验的可比性。其次是修复了两个会**破坏真实内容**的正则 bug（吃书名、吞中文邮箱）。

## 附：文件与术语对照

| 名称 | 含义 |
|---|---|
| `cat_l1` | 一级大类（7 类），模型预测目标 |
| `label` | 情感标签：0 = 负面，1 = 正面 |
| `class.txt` | 7 个大类名，行序 = 标签编号 |
| 分层键 | 划分数据集时用于保持各类占比一致的键，本项目中为 `cat_l1 + label` |
| support | 某一类别（或某格子）的真实样本数，评估指标必须与它一起给出 |
